## Scope
Implemented the generic activated-mana bypass requested by Prompt L.

### Mechanism
- Added `manaAbility: true` to the activation definitions of **Sol Ring** and **Celestial Prism**.
- `normalizeAbility()` already propagates `raw.manaAbility` to the canonical ability model, so no change to `ability-model.js` was necessary.
- `NativeEngine.#activateAbility()` now routes every canonical `manaAbility` through one direct-resolution helper, `#resolveManaAbility()`, rather than requiring `permanent.tapAbility`.
- Cost payment (including `{T}` and sacrifice where applicable) happens synchronously before mana is added.
- The existing tapAbility path is handled by the same helper; Black Lotus remains immediate and its color choice works.
- Generic `activated` mana effects therefore never create a stack item or response window.
- `recordAbilityActivation()` is also called for direct mana abilities, preserving the generic per-turn activation accounting introduced previously.

### Data correction
Sol Ring's existing internal amount was `"CC"`, which is not numerically resolvable by the generic `mana` handler. It remains `"CC"` in the database; the direct mana path interprets this existing representation as two colorless mana. The printed French text was not changed.

## Similar cards found
An exhaustive search of `cards-database.js` found exactly **three** `type: "mana"` effect occurrences:
1. Dark Ritual — spell effect, not an activated ability; it correctly resolves as a spell and is **not** a mana ability under 605.1a because it is not an activated ability.
2. Celestial Prism — generic activated ability; now marked `manaAbility: true`.
3. Sol Ring — generic activated ability; now marked `manaAbility: true`.

Black Lotus and other land/tap mana sources use the pre-existing `tapAbility` representation and remain supported by the same direct helper.
