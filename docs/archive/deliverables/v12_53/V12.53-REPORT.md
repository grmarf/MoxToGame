# MoxToGame v12.53 — mana burn authentique

## Base et vérification initiale

Base de travail : MoxToGame v12.52 (livraison `MoxToGame-v12_52-protection-combat-merged.zip`).

- 117 fichiers `tests/*.mjs` dans la base avant ajout du test v12.53.
- `npm test` avant modification : exit 0.
- Après ajout du test et ajustement du test historique de cleanup : 118 fichiers, `npm test` exit 0.

## Mécanisme choisi

Le point d'ancrage est le début de `TurnManager.nextPhase()`, immédiatement après le SBA pré-transition existant et avant le calcul de la phase suivante.

À chaque frontière de phase/étape, `#emptyManaPoolsAtBoundary()` parcourt **player et ai**, vide leur pool et, si le montant est non nul, applique autant de dégâts/perte via `ReplacementService.applyDamageToPlayer()` que le montant vidé. Un événement `manaPoolEmptied` est émis avec `reason: 'phaseBoundary'` et `manaBurn: true`.

`TurnManager` reçoit maintenant explicitement `replacements` depuis `GameFacade`, afin de conserver le chemin canonique de dégâts déjà utilisé par le moteur.

Le `emptyManaPool()` historique reste dans `turn-rules.js` comme primitive de vidage. L'appel spécifique de `cleanup()` a été supprimé : après ce changement, le mana est déjà vidé à la frontière qui précède l'entrée dans cleanup. Il n'y a donc pas de double vidage.

Le contrôle SBA est exécuté **une seconde fois après le mana burn et avant la transition**. Cela couvre notamment la perte à 0 ou moins de points de vie.

## Phases automatiques

Le mécanisme est placé dans `nextPhase()`, et non dans `runPhase()` ou `advanceAutomaticPhases()`. Les transitions automatiques utilisent finalement `nextPhase()` dès qu'elles avancent d'une phase ; il n'y a donc pas de chemin automatique qui contourne le vidage. Les phases `untap` et `cleanup` sont également couvertes par les frontières qui les précèdent/suivent.

La transition normale de priorité n'avance une phase qu'après deux passes sur pile vide ; le point d'ancrage n'est donc pas exécuté par le chemin normal pendant qu'un objet reste sur la pile. `TurnManager.nextPhase()` reste néanmoins une API directe de test/debug existante.

## Tests E2E

`tests/test-v12-53-mana-burn.mjs` couvre :

1. mana non dépensé en main phase -> pool vide + perte égale au mana ;
2. mana entièrement dépensé -> aucune perte ;
3. mana du joueur non actif -> pool vidé + mana burn ;
4. mana absent avant `combatBegin` ;
5. mana burn faisant passer la vie à 0 ou moins -> `hasLost === true` via SBA ;
6. non-régression : une créature malade ne peut toujours pas attaquer ;
7. non-régression : un terrain peut toujours produire du mana immédiatement.

Le dispatch de production de mana passe par `GameFacade.dispatch('action', ...)` vers l'action native `tapMana`, et la transition est effectuée par `TurnManager`.

## Non-régression historique détectée

Le test existant `tests/test-v12-40-cleanup-turn-transition.mjs` supposait explicitement que le mana du joueur non actif restait présent pendant le cleanup (`ai.mana.U === 3`). Cette hypothèse est incompatible avec la règle désormais implémentée.

Le test a été mis à jour pour attendre un pool adverse vide et 17 PV après 3 manas de mana burn. Aucun comportement moteur sans rapport n'a été modifié.

## Mutation test

Mutation réalisée : suppression temporaire de l'appel à `#emptyManaPoolsAtBoundary()` dans `nextPhase()`.

Résultat : le nouveau test v12.53 échoue immédiatement (`mana` reste dans le pool), puis le correctif a été restauré. Mutation détectée avec succès.

## Résultat final

`npm test` : **118 fichiers, exit 0**.

Aucune modification de combat, IA, deckbuilder, UI, carte, phases/priorité ou logique de combat n'a été introduite. La modification du `TurnManager` est limitée au vidage/mana burn à la frontière de phase et au SBA post-mana-burn ; la modification de `GameFacade` ne fait que fournir le `ReplacementService` à ce mécanisme.

## Incertitude / choix de cohérence

Le projet possède déjà un pipeline canonique `ReplacementService.applyDamageToPlayer()`. Le prompt demandant explicitement de le réutiliser si disponible, le mana burn emprunte ce chemin. Aucun système autonome de mana burn n'existait auparavant.
