CONSTAT DE DÉPART
En reprenant Prompt Q, la branche "cible joueur" du handler `damageAndGain`
(atomic-effects.js, seule carte concernée : Psionic Blast) était déjà
correctement câblée sur `api.applyDamageToPlayer` -- fix déjà présent dans

revanche, la branche "cible créature" du MÊME handler (pertinente puisque
Psionic Blast a `target:'anyTarget'`, donc peut aussi cibler une créature)
ne vérifiait toujours PAS la protection avant d'appliquer les dégâts
marqués -- exactement le bug BUG-02 original, resté à moitié corrigé.

src/core/effects/atomic-effects.js :
1. Import de `hasProtectionFromColors` depuis continuous-effects.js (ajouté
   à côté de l'import déjà présent de `effectiveTypes`).
2. Handler `damageAndGain`, branche cible créature : ajout de la
   vérification `hasProtectionFromColors(state, target,
   effectiveTypes(state, sourceCard).color)` avant d'appliquer les

   `damageToFliersAndPlayers`.

DÉCOUVERTE IMPORTANTE EN COURS DE CORRECTION -- HORS PÉRIMÈTRE DE CETTE
MISSION, SIGNALÉE ICI EN PRIORITÉ
En écrivant le test de protection, `ctx.api.hasProtectionFromColors` (la
méthode exposée via `buildApi` dans stack.js, ligne ~513) s'est révélée
être une IMPLÉMENTATION SÉPARÉE ET INCOMPATIBLE de la fonction du même nom
importée directement depuis continuous-effects.js :
- La version `ctx.api.*` (stack.js) attend des mots-clés au format
  `protectionWhite`, `protectionBlue`, `protectionBlack`, `protectionRed`,
  `protectionGreen` (camelCase, nom de couleur complet).
- Le format RÉEL utilisé par TOUTES les cartes de cards-database.js est
  `protectionW`, `protectionU`, `protectionB`, `protectionR`,
  `protectionG` (suffixe une lettre) -- vérifié par grep exhaustif sur
  toute la base.
- La version importée directement (continuous-effects.js, ligne ~378)
  gère correctement ce format réel via une table d'alias insensible à la
  casse.

Conséquence concrète vérifiée par un test manuel (Pestilence, capacité
activée `damageAllCreaturesAndPlayers`, contre une créature portant
`protectionB`, source noire) : LA PROTECTION N'EST PAS RESPECTÉE --
la créature subit quand même les dégâts, alors que la même vérification
via la fonction importée directement (combat.js, replacement-effects.js,
et désormais cette mission) fonctionne correctement.

Au moins deux handlers `atomic-effects.js` appellent la version cassée
(`ctx.api.hasProtectionFromColors` / `api.hasProtectionFromColors`) et
sont donc, en pratique, silencieusement non protégés contre les cartes
réelles malgré un appel qui SEMBLE correct à la lecture :
- `damageAllCreaturesAndPlayers` (ligne ~151)
- `damageToFliersAndPlayers` (ligne ~466)
Ces deux sites avaient été classés "déjà corrects" lors du tri AUDIT
initial et à nouveau lors de la vérification externe du Prompt U
(AUDIT-03) -- l'un comme l'autre par lecture de code (présence d'un appel
à `hasProtectionFromColors` avec `effectiveTypes(...).color`), sans test
d'exécution avec le format réel de mots-clés. C'est cette mission qui l'a
révélé, en construisant un test avec une vraie carte et un vrai mot-clé de
protection.

Cette mission n'a PAS corrigé ces deux sites ni la méthode `ctx.api.*` de
stack.js (hors périmètre strict de Prompt Q : "atomic-effects.js
uniquement, et seulement le handler damageAndGain"). C'est pourquoi ma
propre correction utilise l'import direct de `hasProtectionFromColors`
plutôt que `ctx.api.hasProtectionFromColors`, pour ne pas reproduire le
bug dans le code que je viens d'écrire.

RECOMMANDATION -- NOUVELLE MISSION PRIORITAIRE
Une mission dédiée devrait : (1) auditer tous les appelants de
`ctx.api.hasProtectionFromColors` dans tout le projet (au moins
atomic-effects.js:151 et :466 identifiés ici, possiblement d'autres non
cherchés) ; (2) soit corriger la méthode `ctx.api.*` de stack.js pour
qu'elle gère le format réel (`protectionU` etc.), soit migrer tous ses
appelants vers l'import direct de continuous-effects.js et supprimer la
méthode dupliquée de `buildApi` -- à trancher selon ce qui a le plus petit
rayon d'impact. Un test de régression par carte réelle utilisant
`damageAllCreaturesAndPlayers`/`damageToFliersAndPlayers` avec une
créature protégée devrait être ajouté dans tous les cas.

AUTRE POINT NON CORRIGÉ, DÉJÀ SIGNALÉ AILLEURS -- ORACLE DE PSIONIC BLAST
`cards-database.js` modélise Psionic Blast comme "inflige 4 dégâts à
n'importe quelle cible, vous gagnez 4 PV" (`text_fr` et `effect.gain`).
L'Oracle réel (vérifié par recherche externe) est : "Psionic Blast deals 4
damage to any target and 2 damage to you" -- le lanceur subit lui-même 2
dégâts, il ne gagne PAS 4 PV. C'est un bug de DONNÉES DE CARTE (Oracle mal
transcrit), pas un bug moteur, et strictement hors périmètre de Prompt Q
(cards-database.js n'est pas dans les fichiers autorisés). Non corrigé
ici ; à traiter dans une mission de révision de cartes dédiée. Le test de
cette mission a délibérément été construit pour vérifier uniquement le
ROUTAGE des dégâts (protection/prévention), sans valider la sémantique du
gain de vie actuelle, précisément parce qu'elle est déjà connue comme
fausse.
