## Bug 1 — Celestial Prism : mana « any » inutilisable

### Constat reproduit

`Celestial Prism` est `effectStatus: "implemented"` et utilise :

```json
{"cost":"{3}","tap":true,"effect":{"type":"mana","color":"any","amount":1}}
```

Avant correction, le handler générique `mana` indexait directement `mana[effect.color]`. Une résolution réelle créait donc `mana.any`, au lieu de demander la couleur choisie.

Le texte Oracle consulté confirme : **« {2}, {T}: Add one mana of any color. »**. Aucun mana incolore n'est proposé par cette capacité. Source consultée : mtg.wtf, Celestial Prism — Limited Edition Beta. https://mtg.wtf/card/leb/235/Celestial-Prism

### Correction

Dans `src/core/effects/atomic-effects.js`, seul le cas `effect.color === 'any'` a été changé :

- demande réelle via `ctx.api.choose(...)` ;
- options limitées à `['W','U','B','R','G']` ;
- suspension de la résolution lorsque le choix humain n'est pas immédiatement disponible ;
- continuation qui crédite la couleur effectivement choisie ;
- aucune création de `mana.any` ;
- les couleurs fixes conservent le comportement synchrone précédent.

La branche `manaAbility` de `src/core/native-engine.js` n'a pas été modifiée.

### Preuve d'exécution réelle

Le test `tests/test-v12-45-activated-choices-e2e.mjs` :

1. active réellement Celestial Prism ;
2. paie réellement `{3}` et engage le permanent ;
3. résout réellement l'ability sur la stack ;
4. observe une demande `manaColor` avec W/U/B/R/G ;
5. répond réellement `U` ;
6. vérifie `mana.U === 1`, `mana.any === undefined`, stack vide et finalisation unique.

Résultat : **PASS**.

## Bug 2 — Circle of Protection : coût d'activation

Les cinq cartes suivantes ont été corrigées de `{W}` vers `{1}` :

- Circle of Protection: Black
- Circle of Protection: Blue
- Circle of Protection: Green
- Circle of Protection: Red
- Circle of Protection: White

La source Oracle consultée confirme notamment pour Black : **« {1}: The next time a black source of your choice would deal damage to you this turn, prevent that damage. »**. Même coût pour le cycle des cinq couleurs. Source : mtg.wtf, Circle of Protection: Black — Limited Edition Beta. https://mtg.wtf/card/leb/10/Circle-of-Protection-Black

Le test E2E active réellement Circle of Protection: Black, paie `{1}` avec un mana blanc disponible, résout le bouclier, puis vérifie :

- une source noire infligeant 3 blessures : **0 perte de PV** ;
- le bouclier one-shot est consommé ;
- une source rouge infligeant 2 blessures ensuite : **2 PV perdus**.

Résultat : **PASS**.

### Découverte technique complémentaire nécessaire au test

Le handler `preventNextDamageFromColor` existant était bien présent, mais son accès à `ctx.api.replacements` n'était pas exposé par `StackController.#buildApi()`. Cela rendait le handler inopérant en exécution E2E malgré sa présence dans le registre.

Correction minimale dans `src/core/stack.js` : exposition de `replacements: stack.replacements` dans l'API de résolution. Le handler lui-même n'a pas été modifié.

Cette correction est nécessaire pour que le mécanisme de prévention déjà existant fonctionne réellement dans le chemin de résolution de la stack.

## Circle of Protection: Artifacts

La source Oracle confirme : **« {2}: The next time an artifact source of your choice would deal damage to you this turn, prevent that damage. »**. Source : mtg.wtf, Circle of Protection: Artifacts — Fourth Edition. https://mtg.wtf/card/4ed/13/Circle-of-Protection-Artifacts

La carte actuelle de la base a bien le texte `{2}`, mais aucune capacité `activated` et donc `effect: {}` n'est pas matérialisé comme capacité jouable.

J'ai volontairement **laissé cette carte non implémentée** dans v12.45 :

- il faut modéliser un choix de **source artefact** réelle ;
- le helper existant `preventNextTwoDamageFromArtifact` ne correspond pas à l'Oracle : il limite à 2 blessures alors que le texte prévient les blessures de la prochaine source choisie ;
- le handler couleur actuel ne suffit donc pas tel quel.

Ce point dépasse le correctif de coût demandé et mérite une petite extension sémantique dédiée plutôt qu'un branchement trompeur sur le helper existant.

## Tâche 3 — audit des capacités activées avancées

Audit borné aux cartes dont `effectStatus` est `implemented` ou `functional`, et uniquement leurs `activated`.

Résultat de l'inspection de la base : **21 cartes / 21 capacités activées** dans cette population.

Le seul cas où une décision humaine de choix de résultat était encodée mais non demandée par le moteur est :

- **Celestial Prism** — `effect.type = mana`, `color = any` : production d'un faux `mana.any` au lieu d'un choix de couleur réel.

Aucun autre cas de choix de résultat silencieusement auto-résolu ou rendu inutilisable n'a été trouvé dans cette population. Les autres capacités ciblées (`anyTarget`, `anyPermanent`, etc.) passent par le mécanisme de ciblage existant et ne constituent pas un second cas de choix de couleur/mode ignoré par le handler.

Recherche directe dans la base : **une seule occurrence** du motif mana `color: "any"` : Celestial Prism.
