# MoxToGame v12.62 — AUDIT-05 REPORT

## Mission
Correction de `sacrifice: "self"` dans `CostSystem`.

## Vérification avant correction
Le code de `#choosePermanent()` excluait le permanent source lorsque `req === 'self'` :
le filtre générique imposait `p.uid !== context.permanent.uid`. Ainsi, avec une seule carte,
aucune cible n'était trouvée ; avec plusieurs permanents, le premier permanent différent de la
source pouvait être choisi.

Le test `tests/test-v12-62-sacrifice-self.mjs` a été exécuté avant correction et a échoué sur
le premier scénario : la capacité n'était pas considérée payable.

## Modification
Fichier modifié : `src/core/costs/cost-system.js` uniquement.

- `#hasSacrificeTarget()` traite désormais `req === 'self'` explicitement et vérifie que
  `context.permanent` est bien présent sur le champ de bataille.
- `#choosePermanent()` traite `req === 'self'` avant le filtre générique et retourne directement
  `context.permanent` lorsqu'il est présent sur le champ de bataille.
- Le filtre générique `candidates` et les autres formes de `req` (`true`, objet avec `uid`,
  chaîne libre, nombre) restent inchangés dans leur logique.
- `#hasZoneTarget()` n'a pas été modifié.

## Tests
### Test dédié
Commande :

    node tests/test-v12-62-sacrifice-self.mjs

Résultat :

    OK V12.62.1: sacrifice:"self" seul — source sacrifiée par uid.
    OK V12.62.2: sacrifice:"self" avec autre permanent — source sacrifiée, autre permanent conservé.
    OK: V12.62 sacrifice:"self" — deux scénarios E2E validés.

### Suite complète
Commande :

    npm test

Résultat : **exit 0**.

Les tests existants contenant `sacrifice` ont également été exécutés par la suite complète,
notamment les scénarios `sacrificeOrDamage`, les coûts de sacrifice et le test de rollback des coûts.

## Couverture des deux cas du bug
1. Source seule sur le champ de bataille : le paiement est accepté et le permanent source est
   déplacé au cimetière. Le `uid` avant changement de zone est vérifié via `previousUid`, car
   `ZoneManager` attribue normalement une nouvelle identité lors d'un changement de zone.
2. Source + autre permanent : la source est déplacée au cimetière et l'autre permanent reste
   sur le champ de bataille.

Le second scénario confirme explicitement le défaut plus grave : avant correction, plusieurs
permanents permettaient de sélectionner un permanent différent de la source.

## Carte réelle
Une recherche de `cards-database.js` n'a trouvé aucune carte utilisant actuellement
`sacrifice: "self"`. Le test utilise donc une capacité synthétique minimale, mais passe par les
services réels du `GameFacade`/`CostService` et par le `ZoneManager` réel pour le déplacement.

## Limitation constatée et non modifiée
Le chemin `NativeEngine.#activateAbility()` reconstruit actuellement le coût transmis à
`CostService.pay()` avec seulement `mana` et `tap`, ce qui ne transmet pas un éventuel champ
`sacrifice` de l'ability au paiement. Ce point est **hors périmètre** de la mission et aucun
fichier hors `cost-system.js` n'a été modifié. Le test valide donc directement le paiement
canonique via le `CostService` réel après avoir obtenu l'ability via `GameFacade`.
Cette anomalie doit faire l'objet d'une mission séparée si le moteur doit supporter des capacités
activées dont le coût contient `sacrifice: "self"` de bout en bout via `NativeEngine`.

## Fichiers volontairement non modifiés
- `src/core/native-engine.js` : chemin d'activation qui ne relaie pas actuellement `sacrifice` dans
  le coût — hors périmètre.
- `src/core/ability-model.js` : aucun changement nécessaire pour la correction demandée.
- `src/core/zone-manager.js` : comportement de nouvelle identité au changement de zone correct et
  utilisé tel quel.
- Tous les autres traitements de `#choosePermanent()` : hors périmètre et non modifiés.

## Conclusion
**AUDIT-05 corrigé dans le périmètre autorisé.** Le bug d'impayabilité du cas solitaire et le bug
plus grave de sélection d'un autre permanent avec plusieurs permanents sont couverts par une
régression permanente. Suite complète verte.
