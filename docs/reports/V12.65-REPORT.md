DÉCOUVERTE IMPORTANTE EN COURS DE CORRECTION -- HORS PÉRIMÈTRE DE CETTE
MISSION, SIGNALÉE ICI EN PRIORITÉ
En écrivant le test de protection, `ctx.api.hasProtectionFromColors` (la
méthode exposée via `buildApi` dans stack.js, ligne ~513) s'est révélée
être une IMPLÉMENTATION SÉPARÉE ET INCOMPATIBLE de la fonction du même nom
importée directement depuis continuous-effects.js :
- La version `ctx.api.*` (stack.js) attend des mots-clés au format
  `protectionWhite`, `protectionBlue`, `protectionBlack`, `protectionRed`,
  `protectionGreen` (camelCase, nom de couleur complet).
- Le format RÉEL utilisé par TOUTES les cartes de cards-database.js est
  `protectionW`, `protectionU`, `protectionB`, `protectionR`,
  `protectionG` (suffixe une lettre) -- vérifié par grep exhaustif sur
  toute la base.
- La version importée directement (continuous-effects.js, ligne ~378)
  gère correctement ce format réel via une table d'alias insensible à la
  casse.

Conséquence concrète vérifiée par un test manuel (Pestilence, capacité
activée `damageAllCreaturesAndPlayers`, contre une créature portant
`protectionB`, source noire) : LA PROTECTION N'EST PAS RESPECTÉE --
la créature subit quand même les dégâts, alors que la même vérification
via la fonction importée directement (combat.js, replacement-effects.js,
et désormais cette mission) fonctionne correctement.

Au moins deux handlers `atomic-effects.js` appellent la version cassée
(`ctx.api.hasProtectionFromColors` / `api.hasProtectionFromColors`) et
sont donc, en pratique, silencieusement non protégés contre les cartes
réelles malgré un appel qui SEMBLE correct à la lecture :
- `damageAllCreaturesAndPlayers` (ligne ~151)
- `damageToFliersAndPlayers` (ligne ~466)
Ces deux sites avaient été classés "déjà corrects" lors du tri AUDIT
initial et à nouveau lors de la vérification externe du Prompt U
(AUDIT-03) -- l'un comme l'autre par lecture de code (présence d'un appel
à `hasProtectionFromColors` avec `effectiveTypes(...).color`), sans test
d'exécution avec le format réel de mots-clés. C'est cette mission qui l'a
révélé, en construisant un test avec une vraie carte et un vrai mot-clé de
protection.

Cette mission n'a PAS corrigé ces deux sites ni la méthode `ctx.api.*` de
stack.js (hors périmètre strict de Prompt Q : "atomic-effects.js
uniquement, et seulement le handler damageAndGain"). C'est pourquoi ma
propre correction utilise l'import direct de `hasProtectionFromColors`
plutôt que `ctx.api.hasProtectionFromColors`, pour ne pas reproduire le
bug dans le code que je viens d'écrire.

# AUDIT-08 — Déplacements de zones directs contournant ZoneManager

## Statut

**CORRIGÉ ET VALIDÉ — 7 septembre 2026**

La base de travail est le ZIP V12.65 fourni pour reconstruction. L'audit a
porté sur les six sites explicitement demandés dans `native-engine.js` et
`stack.js`.

## Option / méthode retenue

Le principe appliqué est celui demandé par la mission : lorsqu'un
`ZoneManager` est disponible, le déplacement passe par lui ; en son absence,
le comportement brut historique est conservé comme fallback.

Deux sites nécessitaient effectivement une modification dans la base fournie :

1. `src/core/native-engine.js` — `NativeEngine.loadDeck()` : la pioche
   initiale utilisait directement `library.pop()` + `hand.push()`. Elle utilise
   désormais `this.zoneManager.move(card, 'hand', { toSide: side, reason: 'draw' })`
   lorsque le service est disponible.
2. `src/core/stack.js` — `buildApi().createToken()` : la création de token
   poussait directement dans `battlefield`. Elle utilise désormais
   `stack.zones.enterBattlefield(token, side, { controller: side,
   reason: 'tokenCreated' })` lorsque le service est disponible.

Les quatre autres sites demandés dans les deux blocs de finalisation de sorts
étaient déjà conformes dans la base V12.65 fournie : ils testent
`this.zones`, utilisent `moveToGraveyard()` et conservent exactement leur
fallback brut dans les branches `catch` / `else`. Ils ont été vérifiés mais
volontairement laissés inchangés afin de respecter le périmètre et de ne pas
réécrire du code déjà correct.

## Recensement des six sites

| Site | Opération | État après audit | Méthode ZoneManager | Fallback sans ZoneManager |
|---|---|---|---|---|
| `native-engine.js:~393` | pioche initiale `library -> hand` | **corrigé** | `this.zoneManager.move(card, 'hand', {toSide: side, reason: 'draw'})` | `hand.push(library.pop())`, inchangé |
| `stack.js:~366` | aura fizzle, premier chemin | **déjà conforme** | `this.zones.moveToGraveyard(card, {toSide: item.controller, reason: 'fizzleNoTarget'})` | push brut dans `catch` / `else`, inchangé |
| `stack.js:~368` | aura fizzle, fallback sans zones | **déjà conforme** | N/A quand zones absent | push brut historique, inchangé |
| `stack.js:~415` | sort non-permanent, erreur ZoneManager | **déjà conforme** | `this.zones.moveToGraveyard(card, {toSide: item.controller, reason: 'spellResolved'})` | push brut dans `catch`, inchangé |
| `stack.js:~417` | sort non-permanent, fallback sans zones | **déjà conforme** | N/A quand zones absent | push brut historique, inchangé |
| `stack.js:~470` | `createToken` | **corrigé** | `stack.zones.enterBattlefield(token, side, {controller: side, reason: 'tokenCreated'})` | `state[side].battlefield.push(token)` + événement historique, inchangé |

Les lignes exactes peuvent varier légèrement selon le contenu du fichier ;
les six opérations ont été retrouvées par recherche du code, et non par
confiance dans les numéros de ligne de la mission.

## Pourquoi les quatre pushes de cimetière n'ont pas été réécrits

La base fournie contenait déjà le patron attendu :

- test de `this.zones` ;
- appel à `moveToGraveyard()` ;
- `catch` avec le push brut existant si le gestionnaire ne peut pas retrouver
  l'objet ;
- branche `else` conservant le fonctionnement des moteurs/tests minimaux qui
  n'injectent aucun `ZoneManager`.

Les modifier aurait donc augmenté le rayon du changement sans apporter de
correction fonctionnelle supplémentaire.

## Tests ajoutés

Nouveau fichier :
`tests/test-v12-65-zonemanager-tokens-draw.mjs`

Il vérifie :

1. `createToken` via le vrai `StackController` et son API réelle, avec passage
   par `ZoneManager.enterBattlefield()` et identité UID/objectId cohérente.
2. La pioche initiale de `NativeEngine.loadDeck()` via `ZoneManager.move()`,
   avec `previousUid`, `previousObjectId`, `zoneChangeId` et `zoneHistory`.
3. Le chemin d'erreur/fallback de finalisation d'un sort et la conservation de
   l'UID/objectId quand `ZoneManager` ne peut pas retrouver l'objet.
4. Le comportement sans `ZoneManager`, qui reste le push brut historique.

## Validation exécutée

- `node tests/test-v12-65-zonemanager-tokens-draw.mjs` → **PASS**
- `npm test` → **PASS, exit 0**

Les tests existants de zones, tokens et pioche présents dans la suite ont
également été exécutés par `npm test` et restent verts.

## Fichier ZoneManager

`src/core/zone-manager.js` n'a **pas été modifié**.

Ses signatures existantes utilisées par cette correction sont :

- `move(obj, toZone, options)` pour la pioche ;
- `enterBattlefield(card, side, options)` pour les tokens ;
- `moveToGraveyard(obj, options)` pour les chemins de résolution déjà
  conformes.

## Point hors périmètre à conserver pour un futur audit

Un autre handler `createToken` existe dans
`src/core/effects/token-historical-effects.js` et effectue lui aussi un
`ctx.state[side].battlefield.push(token)` direct.

Il n'a **pas été modifié**, conformément aux fichiers autorisés par AUDIT-08.
Ce site devra être traité dans une mission séparée si l'objectif devient
l'élimination exhaustive de tous les déplacements de zone directs du moteur.

## Conclusion

AUDIT-08 est validé sur la base V12.65 reconstruite : les deux déplacements
qui contournaient effectivement `ZoneManager` dans le périmètre autorisé sont
désormais routés par celui-ci, tandis que les quatre chemins de cimetière déjà
conformes et tous les fallbacks sans `ZoneManager` restent inchangés.
