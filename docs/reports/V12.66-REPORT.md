# MoxToGame V12.66 — Rapport de livraison
## Unification de `hasProtectionFromColors`

### Mission

Corriger les deux handlers `damageAllCreaturesAndPlayers` et
`damageToFliersAndPlayers`, qui utilisaient encore la seconde implémentation
de `hasProtectionFromColors` exposée par `ctx.api`.

La base de départ est `MoxToGame-v12_65-damageandgain-protection.zip`.

---

## 1. Audit préalable

Deux implémentations concurrentes existaient :

1. `src/core/continuous-effects.js`
   - `hasProtectionFromColors(state, permanent, sourceColors)`
   - lit les **caractéristiques effectives** via `effectiveKeywords(...)`
   - possède une table d'alias insensible à la casse
   - reconnaît notamment le format réel de la base :
     `protectionW`, `protectionU`, `protectionB`, `protectionR`,
     `protectionG`

2. `src/core/stack.js`, dans `buildApi`
   - `ctx.api.hasProtectionFromColors(perm, sourceColors)`
   - utilisait une table indépendante limitée aux formes
     `protectionWhite`, `protectionBlue`, `protectionBlack`,
     `protectionRed`, `protectionGreen`
   - ne relisait pas les caractéristiques effectives
   - contenait en plus un chemin spécial pour les auras
     `auraEffect.type === 'addProtection'`

La recherche exhaustive des appelants avant correction a donné :

### Version canonique — `continuous-effects.js`

- `src/core/combat.js` ligne ~141
- `src/core/combat.js` ligne ~156
- `src/core/replacement-effects.js` ligne ~78
- `src/core/effects/atomic-effects.js` ligne ~453 (`damageAndGain`)
- usage indirect de `drainLife` via le même import

### Version concurrente — `stack.js`

- `src/core/effects/atomic-effects.js` ligne ~151
  (`damageAllCreaturesAndPlayers`)
- `src/core/effects/atomic-effects.js` ligne ~470
  (`damageToFliersAndPlayers`)

La base de cartes a également été contrôlée : les protections utilisent bien
le format court à une lettre (`protectionW/U/B/R/G`).

---

## 2. Option retenue : Option A

**Option A a été choisie.**

La méthode `hasProtectionFromColors` concurrente de `stack.js` a été supprimée
et les deux appelants restants ont été migrés vers l'import direct de la
fonction canonique de `continuous-effects.js`.

### Pourquoi Option A ?

C'est le plus petit rayon d'impact conceptuel et le meilleur choix
architectural :

- il n'existe plus qu'une seule implémentation du concept ;
- la vérification passe partout par les caractéristiques effectives ;
- le format réellement utilisé par `cards-database.js` est déjà correctement
  géré par cette implémentation ;
- les deux nouveaux sites rejoignent exactement les chemins déjà validés
  (`combat`, `replacement-effects`, `damageAndGain`, `drainLife`) ;
- on supprime une divergence future possible entre deux tables d'alias.

La fonctionnalité d'aura `auraEffect.type === 'addProtection'` de l'ancienne
version 2 n'est actuellement utilisée par aucune carte de
`cards-database.js`, ni par aucun test recherché dans le projet. Elle était
donc du code mort au moment de cette mission.

## 7. Troisième représentation orpheline — laissée volontairement intacte

Un troisième mécanisme, indépendant des deux implémentations de
`hasProtectionFromColors`, existe dans :

`src/core/effects/replacement-card-effects.js`

Le handler `reg('addProtection', ...)` écrit directement :

`target.protectionFrom = [...]`

Ce champ `protectionFrom` est distinct des mots-clés
`protectionW/U/B/R/G`.

Les recherches effectuées pour cette mission montrent qu'aucune carte actuelle
de `cards-database.js` n'utilise ce mécanisme comme `addProtection`, et qu'il
n'est donc pas nécessaire à la protection actuellement représentée par les
cartes.

**Ce mécanisme n'a volontairement pas été fusionné, supprimé ou modifié.**

Il est documenté ici comme **dead code actuellement orphelin**, afin qu'une
future mission puisse le traiter séparément si une carte venait à l'utiliser.

Le même constat vaut pour l'ancien chemin d'aura
`auraEffect.type === 'addProtection'` supprimé avec l'implémentation V2 :
aucune carte ni test actuel ne l'utilise.
